# CQU-SRTP 失物招领系统

**图像感知匹配 + 文本标签匹配** 的校园失物招领平台。Web 前端（Jinja2 + 原生 JS）、
Python / Flask 后端、SQLite 数据库，零外部服务、零构建步骤。

> 核心思路：丢东西的人往往只有一张随手拍的照片和几句描述；捡到东西的人也一样。
> 系统需要在这两条**弱信息**之间建立可靠的对应关系，并把「为什么认为它们匹配」
> 用人话讲清楚，交给人工做最后确认。

## 快速开始

### 方式一：一键启动（Windows）

```bat
start.bat
```

`start.bat` 是一个**纯 ASCII** 的极简启动器，它调用 `serve.py` 完成全部工作：

1. 依赖自检，缺失时自动调用 `bootstrap.py` 安装（无需 pip）
2. 首次运行（无 `data/lostfound.db`）时自动写入演示数据
3. 启动服务并打印访问地址

> **为什么批处理里一句中文都没有？**
> `cmd.exe` 用 **OEM 代码页**（中文 Windows 上是 936/GBK）解析 .bat 文件。
> 若 .bat 以 UTF-8 保存且含中文，cmd 会把中文字节按 GBK 解码成乱码，
> 再把乱码当命令执行，于是刷出满屏
> `'xx' is not recognized as an internal or external command`。
> 因此本项目约定：**批处理只允许 ASCII（无 BOM、CRLF 行尾），
> 所有中文提示都放在 Python 侧**。修改 `start.bat` 时请遵守这条约定。

`serve.py` 也可单独使用：

```bash
python serve.py            # 自检 + 首次自动灌数据 + 启动
python serve.py --reset    # 启动前强制重建演示数据
python serve.py --no-seed  # 首次运行也不灌演示数据（空库启动）
```

### 方式二：手动

```bash
python bootstrap.py     # 免 pip：自动下载 Flask 等依赖并解压到 vendor/
python seed.py --reset  # 生成 20 条演示数据（含程序化合成的照片）
python run.py           # 启动，默认 http://127.0.0.1:5000
```

如果你已有可用的 pip 环境，也可以直接：

```bash
pip install -r requirements.txt
python seed.py --reset
python run.py
```

> `run.py` 在端口被占用时会自动向后寻找可用端口，并在控制台打印实际地址。

打开 <http://127.0.0.1:5000> 即可。演示账号：

| 账号 | 密码 | 角色 |
| --- | --- | --- |
| `demo` | `demo1234` | 普通用户 |
| `admin` | `demo1234` | 管理员（可全量重算匹配、删除任意记录） |

> 浏览、检索、查看匹配结果**无需登录**；发布信息需要登录，避免虚假信息干扰匹配结果。

## 移动 / 重命名项目文件夹

**可以直接剪切粘贴、随便改名**（中文名、带空格都可以），路径不用改代码。
所有路径都由文件位置推导（各模块里的 `BASE_DIR = dirname(abspath(__file__))`），
源码中没有任何硬编码绝对路径。

跟着文件夹一起走的：数据库（`data/`）、上传的图片（`static/uploads/`）、
自带依赖（`vendor/`）。所以换台电脑、换个目录，数据都还在。

**唯一会失效的是 `.venv`** —— 虚拟环境内部记录的是创建时的绝对路径。
移动后有三种处理方式，任选其一：

```bash
# 方案 A（推荐，最省事）：删掉 .venv，直接用系统 Python + 自带 vendor/ 依赖
rmdir /s /q .venv

# 方案 B：原地重建 .venv
python serve.py --recreate-venv

# 方案 C：确认一下当前目录能不能直接跑
python serve.py --check
```

`start.bat` 已经能自动处理这种情况：它会依次尝试
`.venv\Scripts\python.exe` → `py -3` → `python`，用 `serve.py --probe` 逐个探测，
找到能用的那个再启动，所以即使 `.venv` 失效也不会报错崩溃。

**移动后的自检**：

```bash
python serve.py --check
```

会打印项目根目录、vendor 位置、数据库路径、图片数量、`.venv` 健康状态，
并给出结论。用中文目录名实测通过：

```
  ✓ 项目根目录  D:\SRTP-失物招领-2024\
  ✓ vendor 依赖 D:\SRTP-失物招领-2024\vendor
  ✓ 数据库文件  D:\SRTP-失物招领-2024\data\lostfound.db
  ✓ 上传目录    D:\SRTP-失物招领-2024\static\uploads
[虚拟环境]
  ○ 没有 .venv（本项目不依赖它，vendor/ 已足够）
结论：✓ 当前目录可以直接运行 —— python serve.py
```

> 两个小提醒：目标机器需要 **Python 3.10+**；如果目标目录在
> `C:\Program Files\` 这类需要管理员权限的位置，数据库写入可能被拒，
> 放到用户目录下即可。

## 功能一览

**信息发布与检索**

- 发布寻物启事 / 失物招领，支持最多 4 张照片（点击选择、拖拽、`Ctrl+V` 粘贴）
- 分类、颜色、地点、时间、联系人；标签采用芯片式输入并给出常用标签建议
- 列表页支持关键词、分类、类型、排序（最新 / 最早 / 最多浏览 / 匹配度）与分页
- 详情页展示物品信息、图像感知特征（轮廓指纹、主色、主体占比）与联系方式

**智能匹配**

- 发布即刻触发全库比对，返回候选列表并给出可读的匹配理由
- 详情页可「重新计算」，管理端可全量重算并查看性能指标（组/秒）
- 每条匹配展示图像 / 文本 / 地点三条通道的分项得分与融合权重
- 匹配结果缓存进 `matches` 表，列表页用 `items.match_top` 冗余字段直接展示

**算法演示台**（`/algorithm`）

- 左右两侧任意输入两条记录（可临时上传图片），实时查看各通道得分与匹配理由
- 三个权重滑块可现场调参，观察权重变化对总分的影响；不写库，可反复试算

**其他**

- 会话鉴权（PBKDF2 口令哈希 + Flask session），未登录用户只读
- JSON REST API，便于脚本或移动端接入
- 响应式布局，移动端可用

## 匹配算法

```
总分 = w_image · 图像感知分 + w_text · 文本标签分 + w_location · 地点语义分
```

默认权重 `w = (0.45, 0.50, 0.05)`。**任一侧没有照片时，图像权重按比例让渡给文本与地点**
（例如纯文本记录变成 `w_text ≈ 0.95`），保证缺图记录依然能被召回。

### 一、图像感知通道

| 步骤 | 做法 | 解决的问题 |
| --- | --- | --- |
| 前景分割 | 四角像素估计背景色 → 与背景的归一化距离 → `median + 3×1.4826×MAD` 鲁棒阈值 → 中值滤波 → 最大连通域 | 背景（桌面/地面）常占画面 60% 以上，直接比对会让背景主导相似度 |
| 轮廓指纹 | 前景掩膜等比归一化到 16×16 网格（保持长宽比、居中），得 256 位指纹；Dice 系数比对 | 与拍摄距离、画面位置、分辨率无关 |
| 填充率 | 前景像素数 / 包围盒面积（方块≈1.0、圆≈0.79、三角≈0.5） | 补上「轮廓归一化后方形与圆形难以区分」的缺口 |
| 颜色直方图 | 仅取 HSV 的**色相**，16 维环形软分箱，直方图相交率 | 只取色相是因为饱和度会被曝光直接带动（见下） |
| 主色一致性 | 加权的 H/S/V 距离 | 描述「深红 vs 浅红」这类亮度差异 |
| 整图 pHash | DCT 低频 64 位指纹 + 汉明距离 | **仅作弱提示（10%）**：它只擅长判断「是不是同一张照片」 |

图像通道内部权重：`0.40 · 轮廓 + 0.50 · 颜色 + 0.10 · pHash`

### 二、文本标签通道

中文没有空格分词，且失物描述极短。为此不引入 jieba，而是采用**字符级 + 词级混合**方案：

- **分词**：中文单字 + 相邻双字同时入袋（单字保召回，双字提供语序信息），英文/数字整词入袋，
  停用词与单字母噪声过滤，并做同义词归一化（`蓝牙耳机→耳机`、`一卡通→校园卡`、`书包↔背包`）
- **TF-IDF 余弦**：在「目标 + 全部候选」语料上拟合 IDF，避免单物品语料导致权重退化
- **标签重合度**：Dice 系数 + 字符二元组模糊等价（`黑色耳机 ≈ 耳机`）
- **token 重合度**：加权重合（bigram 权重高于 unigram），对错别字与语序差异更宽容

文本通道内部权重：`0.50 · TF-IDF + 0.32 · 标签 + 0.18 · token`

### 三、地点语义

字符串包含关系 > 地点提示词命中（教学楼/图书馆/食堂/宿舍…）> token 重合。
只作为小幅加成（5%），防止「同一栋楼里丢的两个黑色耳机」被误判为同一物品。

### 四、可解释性

失物招领是高敏感场景：只给一个黑盒百分比无法让用户信服，也可能导致误领。
因此每条匹配都会输出人类可读的证据，例如：

- 物品轮廓高度吻合（轮廓 Dice 92%）
- 物品颜色分布几乎相同（直方图相交 96%）
- 两侧图像主色均为「黑色」
- 标签命中：黑色、书包、图书馆
- 遗失/拾取地点吻合

## 效果评测

```bash
python eval_match.py            # 量化评测（P@1 / 阈值扫描 / 通道区分度）
python eval_match.py --verbose  # 额外打印图像子通道分解
```

`seed.py` 生成 8 组「同一物品」的失物/拾物配对（**不同背景、不同尺度、不同曝光**，
模拟两个人各自拍照），另有 5 条同类干扰项与 3 条纯文本记录。
`eval_match.py` 以此构造 9 组正样本 + 135 组负样本：

```
P@1        : 9/9 = 100.0%   （正确对象排名第一）
Recall@3   : 9/9 = 100.0%   （正确对象进入前三）
平均排名    : 1.00

分数分布
  正样本  min 0.557 · 中位 0.726 · max 0.823
  负样本  min 0.003 · 中位 0.156 · max 0.575
  负样本中高于「最低正样本分」的数量：1/135

阈值  0.55 → 精确率 0.900 / 召回率 1.000
阈值  0.60 → 精确率 1.000 / 召回率 0.889     ← 零误报工作点

通道区分能力（正样本均值 − 负样本均值）
  图像感知  +0.477      文本标签  +0.559      地点语义  +0.816
```

唯一的「误报」是**白色无线蓝牙耳机 ↔ 白色有线耳机**（图像 0.902），
它们在人眼看来也确实高度相似，而且系统仍把真正的配对排在它前面。

性能：`recompute_all` 在 144 组组合上约 **3000+ 组/秒**（单线程 Python）。

## REST API

统一返回 `{"ok": true, ...}` 或 `{"ok": false, "error": "...", "message": "..."}`。

### 鉴权

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/auth/register` | 注册并登录 |
| POST | `/api/auth/login` | 登录 |
| POST | `/api/auth/logout` | 退出 |
| GET | `/api/auth/me` | 当前用户 |

### 数据

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/stats` | 统计概览 |
| GET | `/api/categories` | 分类及各分类记录数 |
| GET | `/api/items` | 列表，支持 `type` `category` `status` `q` `order` `page` `limit` |
| GET | `/api/items/<id>` | 详情（含图片感知特征） |
| POST | `/api/items` | 发布，`multipart/form-data`（`images` 可多值）或 JSON（`images` 传 base64 dataURL） |
| DELETE | `/api/items/<id>` | 删除（仅本人或管理员） |

### 匹配

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/items/<id>/matches` | 该记录的对侧候选，支持 `top_k` `threshold` `w_image` `w_text` `w_location` |
| POST | `/api/items/<id>/match` | 用「临时上传的图片 + 文本」检索库内记录（不落库） |
| POST | `/api/match/pair` | 任意两条记录成对试算（支持 base64 图片，含图像通道） |
| POST | `/api/match/text` | 仅文本试算（不传图片，最轻量） |
| POST | `/api/match/recompute` | 全量重算（仅管理员） |
| GET | `/api/matches/top` | 库内得分最高的匹配对 |

示例：

```bash
# 发布一条拾物（带照片）
curl -X POST http://127.0.0.1:5000/api/items \
  -F "type=found" -F "title=图书馆捡到黑色背包" \
  -F "tags=黑色,背包,图书馆" -F "location=图书馆四楼" \
  -F "images=@photo.jpg"

# 查看匹配结果
curl "http://127.0.0.1:5000/api/items/1/matches?top_k=5"

# 调参试算：只看文本通道
curl -X POST http://127.0.0.1:5000/api/match/text \
  -H "Content-Type: application/json" \
  -d '{"left":{"title":"黑色耳机","tags":["黑色","耳机"]},
       "right":{"title":"白色耳机","tags":["白色","耳机"]},
       "weights":{"image":0,"text":1,"location":0}}'
```

## 数据模型

```
users ──< items ──< item_images
              └──< matches >──┘   (lost_id, found_id 唯一约束)
categories ──< items
```

- `items`：同一张表存寻物启事与失物招领，用 `type` 区分，便于跨类型匹配；
  `tags` 存 JSON 数组，`match_top` 冗余最佳匹配分供列表页直接排序
- `item_images`：整图特征（`phash_*`、`color_hist`、`dominant`）与
  **前景特征**（`shape_sig`、`crop_hist`、`crop_dominant`、`blob_fill`、`blob_ratio`、`blob_box`）
- `matches`：`(lost_id, found_id)` 唯一，缓存得分、证据文案与完整 detail

数据库启动时自动建表；`db.MIGRATIONS` 会在旧库上 `ALTER TABLE` 补齐缺失列，
无需手动删库。

## 设计取舍与踩坑记录

这些结论都由 `debug_*.py` 的实测数据支撑，也写进了对应代码的注释里。

**1. 放弃「裁切后 pHash」作为形状主通道。**
原计划用前景裁剪图的 pHash 做形状比对。实测发现：把物体裁出来之后，主体已占满
裁切框，DCT 低频系数的「与中位数比较」极易受重采样相位影响 —— 同一个方块换尺度后
汉明距离 24~32，而「换成圆形」也只有 21。也就是说该特征几乎没有区分度。
改为**尺度归一化的 16×16 轮廓指纹 + Dice**，同物体各尺度稳定在 0.96 以上。
pHash 保留为整图弱提示。

**2. 背景必须「剔除」而不是「涂黑」。**
用掩膜把背景涂黑会引入巨大的黑色分量 —— 而黑色是合法颜色 —— 结果
「黑色书包 vs 蓝色书包」的差异被抹平。改为按掩膜索引取像素。

**3. 颜色直方图只取色相。**
用 HSV 三维直方图时，同一红色物体整体曝光 +12% 会让前景饱和度均值从 173.6 掉到
162.0，跨过 bin 边界，相交率暴跌到 0.065（颜色明明没变）。改为 16 维色相环形软分箱后
同色变体回到 0.92~1.00，异色仍是 0.00；亮度差异交给主色一致性指标。

**4. 直方图必须软分箱。**
硬分箱下同一个红色在不同缩放下相交率仅 0.047，因为像素整体跳 bin。三角核软分箱后
同为 0.96。色相是环形的，软分箱也在环形空间做，避免红色在 0/360 边界被切两半。

**5. 坐标系必须显式约定。**
前景检测在降采样图（最长边 320）上进行，早期版本把降采样坐标当原图坐标返回，
导致 640×480 图片的掩膜整体偏移到背景上（「黑色书包」的前景主色被算成「浅米色」）。
现在 `object_blob` 的契约写清楚了：掩膜与裁切图取自工作图，包围盒坐标换算回输入图。

**6. BLOB 不能直接进 JSON。**
`sqlite3` 返回 `bytes`，`jsonify` 会抛 `TypeError`。数据层出口统一转十六进制字符串，
`app.json_safe` 再做一层兜底（并有测试守护）。

**7. 权重让渡优于硬性过滤。**
最初想「没有图片就直接跳过图像通道」，但那会让纯文本记录拿不到分数。改为把图像权重
按比例让渡给文本与地点，纯文本记录依然能匹配（测试 `test_publish_text_only_then_match`）。
